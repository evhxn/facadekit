# 10. Web UI: layout rules and the screenshot walkthrough

Written for the first UI revamp after the first hardware test (2026-11-14). It says how the
screens are built and how to check them; it does not repeat the API (`docs/05`).

## Building blocks

| Piece | Where | Use |
|---|---|---|
| Colours, spacing, radius, tap size | `src/theme.css` (`--bg`, `--surface`, `--accent`, `--space-1..6`, `--target`) | Every page. Dark by default, light when the system asks. No colour values in page CSS except the projector page (always black) |
| `Stepper` | `components/Stepper.tsx` | A short wizard: where you are, ticks for finished steps, buttons back to earlier or finished steps only |
| `Checklist` | `components/Checklist.tsx` | What is ready and what is not, each line with one short "what to do" |
| `JobProgress` | `components/JobProgress.tsx` | Any job: its current step, percent, time left (estimated from progress so far), Cancel |
| `ErrorBanner` | `components/ErrorBanner.tsx` | Every error. Always has "Copy diagnostic info" |
| `ScanResultView` | `pages/setup/ScanResultView.tsx` | Scan result with unmeasured parts coloured by reason, and the fix for each |
| `EditorHeader` | `components/EditorHeader.tsx` | Top line of Surfaces, Arrange and Publish: what the page is for, page-wide tools, and "Next →" (highlighted once the step has what the next one needs, with a hint until then) |
| `PageState` | `components/PageState.tsx` | A whole page that cannot show its editor yet: loading, failed (with "Copy diagnostic info"), or waiting for an earlier step ("Scan the house first") |
| `a.button` | `src/theme.css` | A link that goes to another page but looks like a button |

## Rules every screen follows

- **Empty, loading and error states are written out.** A list that is loading says so; an empty list says what to do first; a failed request shows the server's message through `userMessage()` in an `ErrorBanner`.
- **One primary button per state**, and it is the next step.
- **No sideways scrolling** at phone width (the walkthrough checks it on every setup screen).
- **Setup is a card plus a checklist**: the step on the left, "Ready to scan?" on the right. At 900 px and below, the checklist moves under the step.
- **The camera step has three numbered parts**: choose the camera, aim it (live view, projector grid or white, camera settings), check the view.

## Screenshot walkthrough

```bash
cd studio/web && pnpm build && pnpm walkthrough
```

Starts `facadekit serve --sim` on port 8198 with an empty data folder. In Chromium at
1280x800 (dark and light theme) and at Pixel 7 size (dark) it:

1. creates a project and goes through the three setup steps, with a camera check and a scan;
2. on Surfaces, adds a rectangle surface and checks it on the (simulated) house (`09b-surfaces-checked`);
3. on Arrange, imports a test picture, puts it on the timeline and waits for the exact
   preview frame;
4. on Publish, renders the show and waits for it in the list;
5. returns to Projects.

It fails on any page error, and on sideways scrolling on the setup, Arrange and Publish
screens. Screenshots of every screen, empty and filled, go to
`test-results/screens/<dark|light|phone>/` (or `$FACADEKIT_SHOTS`). Software WebGL is
switched on as in the parity run.

It sets `FACADEKIT_NO_CAMERA_PROMPT=1` (also set for `pnpm e2e`) so that starting the server
never makes macOS ask for camera access during a test.

## Light theme

The light theme (used when the system asks for it) was checked on every screen of the
walkthrough. Pictures drawn on canvases (surface outlines, magic-select marks, timeline clips)
keep fixed colours on purpose: they sit on photos and video, not on the page background.
