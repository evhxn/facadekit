# T-117 – Phone remote for fine alignment

- **Milestone:** v1
- **Recommended model:** Sonnet
- **Depends on:** T-032, T-024
- **Parallel with:** T-116

## Goal

Let the user stand in the yard with a phone and nudge surface corners while looking at the house, instead of walking back to the laptop for every adjustment.

## Background

The FacadeKit server binds to `127.0.0.1` by default (no authentication, so it must not be exposed blindly). This ticket adds an explicit, opt-in LAN mode protected by a one-time code, and a small touch-friendly page that only edits surface corners.

## Files to create or modify

- Backend: modify `studio/backend/src/facadekit/cli.py` (`serve --lan`), `api/app.py`, create `api/remote_auth.py`, `tests/test_api_remote.py`
- Web: create `studio/web/src/pages/RemotePage.tsx` (+ test), route `/remote/:projectId`; modify `pages/SurfacesPage.tsx` (button "Use phone as remote")

## Specification

Backend:

1. `facadekit serve --lan` binds to `0.0.0.0` and generates a random 6-digit **pairing code** printed in the terminal and available at `GET /api/v1/remote/info` (only from loopback clients) as `{"enabled": true, "code": "123456", "urls": ["http://192.168.1.20:8137"]}` (`urls` = the machine's non-loopback IPv4 addresses; find them by opening UDP sockets or `socket.getaddrinfo(socket.gethostname(), …)`, and omit duplicates). Without `--lan`: `{"enabled": false, "code": null, "urls": []}`.
2. Access rule (middleware in `remote_auth.py`): requests from loopback addresses (`127.0.0.1`, `::1`) are always allowed. Requests from other addresses are allowed only when LAN mode is on **and** they carry a valid session cookie `fk_remote`; otherwise 403 with code `BAD_REQUEST` and message "Pair this device first". Exempt for everyone: static files of the web UI and `POST /api/v1/remote/pair`.
3. `POST /api/v1/remote/pair` `{"code": "123456"}` → sets cookie `fk_remote=<random 32 hex>` (HttpOnly, SameSite=Strict, 12 h) and returns `{"ok": true}`; wrong code → 403; after 5 wrong attempts from one address, that address is locked out for 5 minutes (429-style: return 403 with message "Too many attempts"). Sessions are kept in memory.
4. Non-loopback sessions are **restricted** to these routes: `GET /projects/{pid}`, `PUT /projects/{pid}`, `POST /projector/show`, `GET /projector/status`, `GET /health`, `/ws/events`. Everything else returns 403 for remote sessions (no file uploads, renders, FPP actions or deletes from the phone). WebSocket handshakes check the same cookie.

Web:

5. Surfaces page: button "Use phone as remote" opens a dialog. If `remote/info.enabled` is false: "Restart FacadeKit with `facadekit serve --lan` to use a phone on your Wi-Fi." Otherwise show each URL + `/remote/<project id>` as text and as a QR code (render with a tiny dependency-free QR generator module `components/qr.ts`; add it as part of this ticket, version 4–6 byte mode with error correction L is enough for these URLs) and the pairing code.
6. `RemotePage` (mobile layout, large touch targets, works in portrait): if not paired, a numeric code input → `pair`. Then: a surface picker (prev/next buttons and name), a corner picker (four big buttons arranged like the corners: TL, TR, BL, BR, plus "All" to move the whole surface), a D-pad of four arrows, and a step selector (1 px / 5 px / 20 px). Holding an arrow repeats every 120 ms. Each nudge updates the project through the existing store (`update` → debounced `PUT`), then calls `projectorShow({mode: "outlines", project_id, selected_id})` (throttled to one in flight). Show connection state and "Saved" feedback.
7. The page listens on `/ws/events` for `project` messages and reloads the project when the revision changed elsewhere (laptop edits), unless it has unsaved local edits.

## Pitfalls

- Never enable LAN binding without the flag. The default remains loopback-only; keep the existing tests for that.
- `request.client.host` behind the Vite dev proxy is always loopback; that is fine for development but note it in a code comment.
- The pairing code is short by design (typed on a phone); the lockout is what makes it acceptable on a home network. Print a line in the terminal when a device pairs.

## Acceptance

```
cd studio/backend && uv run pytest -q tests/test_api_remote.py && uv run mypy src && uv run ruff check .
cd studio/web && pnpm lint && pnpm typecheck && pnpm test
```

Backend tests (simulate client addresses by constructing the app with a `client_addr_override` test hook or by setting `scope["client"]` through a small ASGI wrapper): loopback requests work without a cookie in both modes; a non-loopback request without a cookie → 403; pairing with the right code then `GET /projects/{pid}` → 200; the same session calling `POST /projects/{pid}/renders` → 403; wrong code five times → locked out even with the right code afterwards; LAN mode off → pairing returns 403; `remote/info` from a non-loopback address → 403.

Web tests: QR module encodes `"HELLO"` to a matrix of the expected size (21×21 for version 1; verify the three finder patterns); remote page: after pairing, pressing the right arrow with TL selected and step 5 changes `quad[0][0]` by 5 and calls `projectorShow` with `mode: "outlines"`; "All" moves all four corners; when LAN mode is disabled the dialog shows the restart instruction.

## Out of scope

Internet/remote access outside the LAN, HTTPS, user accounts, editing anything other than surface corners from the phone, using the phone as the calibration camera (v2).
