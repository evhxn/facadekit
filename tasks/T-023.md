# T-023 – Job runner

- **Milestone:** MVP
- **Recommended model:** Sonnet
- **Depends on:** T-003, T-004
- **Parallel with:** T-005 … T-022

## Goal

Run long operations (calibration, render, publish) one at a time on a background thread, tracking state, progress, cancellation and errors so the HTTP API can report on them.

## Files to create

- `studio/backend/src/facadekit/jobs/runner.py`
- `studio/backend/tests/test_jobs_runner.py`

## Interfaces (copied from docs/05-interfaces.md)

Available (`facadekit.models.jobs`):

```python
JobKind = Literal["calibration", "render", "publish", "analyze"]
JobState = Literal["queued", "running", "succeeded", "failed", "cancelled"]
class JobError(BaseModel): code: str; message: str
class Job(BaseModel):
    id: str; kind: JobKind; state: JobState; progress: float = 0.0; message: str = ""
    error: JobError | None = None; result: dict[str, Any] | None = None; created_at: str
utc_now_iso() -> str
```

Also `facadekit.ids.new_id("job")`, `facadekit.errors.FkError(code, message)`.

To implement:

```python
JobFn = Callable[[Callable[[float, str], None], Callable[[], bool]], dict[str, Any]]
#               progress(fraction, message)      cancel() -> bool        returns the result dict

class JobRunner:
    def __init__(self, on_update: Callable[[Job], None] | None = None) -> None: ...
    def submit(self, kind: JobKind, fn: JobFn) -> Job: ...      # returns immediately, state "queued"
    def get(self, job_id: str) -> Job: ...                      # FkError NOT_FOUND
    def cancel(self, job_id: str) -> Job: ...                   # sets the cancel flag; FkError NOT_FOUND
    def shutdown(self) -> None: ...
```

Behaviour:

- One worker thread runs jobs in submission order.
- `fn` returning normally → `succeeded`, `progress = 1.0`, `result` = the returned dict.
- `FkError("CANCELLED", …)` raised by `fn` → `cancelled`. Any other `FkError` → `failed` with that code and message. Any other exception → `failed` with code `INTERNAL` and message `str(exc)`; log the traceback with `logging.exception`.
- Cancelling a queued job marks it `cancelled` immediately and it never runs. Cancelling a finished job is a no-op that returns the job.
- `on_update(job_copy)` is called on every state change, and on progress changes at most 10 times per second per job (always deliver the final state).
- `get` returns a copy (`model_copy(deep=True)`), never the internal object.
- Finished jobs are kept; only the newest 50 jobs are retained.

## Steps

1. Use `queue.Queue` plus a daemon `threading.Thread`; protect the job dict with a `threading.Lock`.
2. Each job has a `threading.Event` cancel flag; the `cancel` callable handed to `fn` is `event.is_set`.
3. The `progress` callable clamps the fraction to 0..1, stores message and fraction, and applies the rate limit using `time.monotonic()`.
4. `shutdown()`: set all cancel flags, push a sentinel, join the thread with a 5 s timeout.
5. Exceptions raised inside `on_update` must not kill the worker: catch and log them.

## Acceptance

```
cd studio/backend && uv run pytest -q tests/test_jobs_runner.py && uv run mypy src && uv run ruff check .
```

Tests (poll with a helper `wait_for(lambda: runner.get(id).state in {...}, timeout=5)`):

- A job returning `{"x": 1}` ends `succeeded` with that result and progress 1.0.
- A job raising `FkError("SCAN_FAILED", "m")` ends `failed` with `error.code == "SCAN_FAILED"`.
- A job raising `ValueError("boom")` ends `failed` with code `INTERNAL`.
- A job looping `while not cancel(): sleep(0.01)` then raising `FkError("CANCELLED", "")` ends `cancelled` after `runner.cancel(id)`.
- Two jobs submitted back to back run sequentially (the second's start timestamp is after the first's end; record with a shared list).
- Cancelling the second job while the first still runs marks it `cancelled` and its function is never called.
- `on_update` receives states in order `queued, running, …, succeeded`; a job that calls `progress` 1000 times in 0.1 s triggers fewer than 20 progress updates.
- `get("job_missing")` → `FkError` `NOT_FOUND`.
- An `on_update` that raises does not prevent the job from finishing.

## Out of scope
